STEP 3

Read the architecture before running it

docker-compose.yml ↗
source_postgres
      ↓ pg_dump
elt_script
      ↓ psql
destination_postgres
      ↓ dbt
analytics models
Host: source=localhost:5433, destination=localhost:5434. Inside Docker: source_postgres:5432 and destination_postgres:5432.
STEP 4

Start only the two PostgreSQL services

docker compose up -d source_postgres destination_postgres
docker compose ps

docker compose logs source_postgres
docker compose logs destination_postgres
Start infrastructure first so you can inspect source and destination independently from ELT.
STEP 5

Explore the source database

init.sql ↗
docker exec -it source_postgres psql -U postgres -d source_db

\dt
SELECT * FROM users;
SELECT * FROM orders;
\q

Baseline: 5 users, 8 orders.

STEP 6

Practice SQL on the source

SELECT COUNT(*) FROM users;
SELECT COUNT(*) FROM orders;

SELECT *
FROM orders
WHERE status = 'paid';

SELECT
    user_id,
    COUNT(*) AS order_count,
    SUM(amount) AS revenue
FROM orders
WHERE status = 'paid'
GROUP BY user_id
ORDER BY user_id;
Understand the source before you validate the destination.
STEP 7

Understand volumes and persistence

docker volume ls
docker compose down
docker compose up -d source_postgres destination_postgres
down removes containers/network, but named volumes survive. down -v removes the volumes too.
STEP 8

Read the ELT Dockerfile

ELT Dockerfile ↗
FROM python:3.11-slim
RUN apt-get update && apt-get install -y postgresql-client
WORKDIR /app
COPY elt_script.py .
CMD ["python", "elt_script.py"]
PostgreSQL client tools are installed because the container needs pg_isready, pg_dump, and psql.
STEP 9

Build the ELT image

docker compose build elt_script
docker images
Dockerfile + elt_script.py → image.
STEP 10

Read the Python ELT control flow

elt_script.py ↗
1. read env
2. wait for source
3. wait for destination
4. pg_dump source
5. psql load destination
6. validate row counts
7. success
subprocess.run(..., check=True) makes external command failures fail the Python process too.
STEP 11

Run the ELT pipeline

docker compose ps
docker compose up --build --abort-on-container-exit elt_script

Look for readiness, pg_dump, psql, row-count validation, and ELT completed successfully.

Python coordinates native PostgreSQL tools; it does not copy rows one by one.
STEP 12

Validate the destination yourself

docker exec -it destination_postgres psql -U postgres -d destination_db

\dt
SELECT COUNT(*) AS users_loaded FROM users;
SELECT COUNT(*) AS orders_loaded FROM orders;

SELECT SUM(amount) AS paid_revenue
FROM orders
WHERE status = 'paid';

SELECT COUNT(*) - COUNT(DISTINCT order_id)
AS duplicate_order_ids
FROM orders;

\q

Baseline: 5 users, 8 orders, paid revenue = 1145.00, duplicate IDs = 0.

STEP 13

Change the source and prove data movement

docker exec -it source_postgres psql -U postgres -d source_db

INSERT INTO users (full_name, email, country)
VALUES ('Practice User', 'practice@example.com', 'Germany');

INSERT INTO orders (user_id, order_date, amount, status)
SELECT user_id, CURRENT_DATE, 99.00, 'paid'
FROM users
WHERE email = 'practice@example.com';

\q

docker compose up --build --abort-on-container-exit elt_script

Then query the destination and confirm the new user/order arrived.

This proves the pipeline actually moves changed data, not merely that the containers start.
STEP 14

Reset and understand init.sql

docker compose down -v
docker compose up -d source_postgres destination_postgres

docker exec -it source_postgres psql -U postgres -d source_db -c "SELECT COUNT(*) FROM users;"

docker compose up --build --abort-on-container-exit elt_script
Removing volumes gives PostgreSQL a fresh data directory, so init.sql runs again.
STEP 15

Install and configure dbt

profiles.yml.example ↗
# PowerShell
py -m venv .venv
.\.venv\Scripts\python.exe -m pip install --upgrade pip
.\.venv\Scripts\python.exe -m pip install dbt-postgres

New-Item -ItemType Directory -Force "$HOME\.dbt"
Copy-Item .\dbt_project\profiles.yml.example "$HOME\.dbt\profiles.yml"

.\.venv\Scripts\dbt.exe --version
dbt runs on your host, so it connects to destination through localhost:5434.
STEP 16

dbt debug and run

sources.yml ↗ stg_users.sql ↗ stg_orders.sql ↗ 
cd dbt_project
..\.venv\Scripts\dbt.exe debug
..\.venv\Scripts\dbt.exe run
source() points to raw external tables. ref() points to another dbt model and creates lineage.
STEP 17

Inspect staging and the customer mart

customer_revenue.sql ↗
docker exec -it destination_postgres psql -U postgres -d destination_db

\dt analytics.*
\dv analytics.*

SELECT * FROM analytics.stg_users ORDER BY user_id;
SELECT * FROM analytics.customer_revenue ORDER BY user_id;

\q
Raw orders = one row per order. customer_revenue = one row per customer. That is a grain change.
STEP 18

Run dbt tests

..\.venv\Scripts\dbt.exe test

Tests cover key assumptions such as uniqueness, non-null keys, and relationships between orders and users.

dbt run asks "can models build?" · dbt test asks "are the modeled data assumptions true?"
STEP 19

Break dbt on purpose and debug it

Temporarily change ref('stg_orders') to ref('stg_orderz') in customer_revenue.sql.

..\.venv\Scripts\dbt.exe run

# from repository root:
git diff -- dbt_project/models/marts/customer_revenue.sql
git restore dbt_project/models/marts/customer_revenue.sql
Failure → read evidence → identify broken dependency → restore → rerun. No random debugging.
STEP 20

Understand Cron and Airflow orchestration

run_elt.sh ↗ elt_dag.py ↗ 
# Cron wrapper (Git Bash / WSL / macOS / Linux)
bash orchestration/cron/run_elt.sh

# Syntax-check Airflow DAG
py -m py_compile orchestration/airflow/elt_dag.py
elt >> dbt_run >> dbt_test
Cron = simple time-based scheduling. Airflow = explicit task graph, retries, history, and orchestration. This repo contains a DAG example, not a complete local Airflow deployment.
